### Q1: 你们为什么不用 LangChain、CrewAI 或 AutoGen 这些成熟框架，而是选择自研核心状态机和调度器？

**【满分回答要点】**：
1. **控制反转与确定性约束**：LangChain/CrewAI 等框架封装了太多隐式 Prompt 逻辑和不可控的重试机制。在金融审计场景下，**“不可复现、不可解释、状态丢失”是死罪**。我们必须对每一步推理的状态（Working/Episodic Memory）、执行上下文与错误栈拥有 100% 的绝对控制权。
2. **状态回滚与反事实自愈 (Reflexion)**：自研的 ToT/MCTS 状态树支持深度的状态快照、回滚和父子节点剪枝，这是现成黑盒多智能体框架极难低开销实现的。
3. **性能与包袱解耦**：自研轻量级架构启动只需 50ms，且无冗余依赖，生产环境镜像体积缩小 65%，利于在金融私有化或微服务环境敏捷部署。

### Q2: 既然 LLM 不擅长心算，业界常用的做法是给 LLM 配 Calculator Tool。你们的“Code-as-Action + DuckDB 沙箱”相比普通工具调用有何本质优势？

**【满分回答要点】**：
1. **多表关联与复杂聚合的表达力维度差异**：Calculator Tool 只能做标量计算（如 $A + B$）。但真实财报包含跨期（三年一期）、跨表（资产负债表与现金流量表）的上百个科目联合验算。将财报转化为 DuckDB 列式内存表后，LLM 可以生成标准的 SQL 或带有 Pandas 聚合的 Python 代码，单次沙箱即可完成几十步计算，极大避免了多轮 Tool Calling 带来的累积上下文膨胀。
2. **杜绝中途幻觉注入**：传统 Tool-Calling 会把计算结果作为纯文本传回 LLM，模型在复述过程中仍然可能产生“读错数字”的二次幻觉；而我们的沙箱直接生成法庭级校验布尔值与绝对误差值，直接更新证据链状态。
3. **AST 安全守卫**：我们的沙箱通过 Python `ast` 模块进行了严格的字节码与模块白名单过滤，切断网络请求（Zero Internet）、禁止 `os/sys` 危险调用，并设有线程级 CPU/内存超时硬限制，杜绝恶意财报代码注入。

### Q3: 门房认知路由器（Cognitive Router）的分流逻辑是什么？如何确保路由本身不会产生巨大的延迟和成本？

**【满分回答要点】**：
1. **分级设计依据**：
   - **Tier 1 (直觉级)**：单一事实查询（如“茅台2023年董事长是谁”），仅走 Hybrid RAG 极速检索，无需沙箱，耗时 < 100ms；
   - **Tier 2 (规范级)**：标准会计勾稽核算（如资产负债表平衡公式、杜邦分析），走确定性状态机单流计算，耗时 < 300ms；
   - **Tier 3 (刑侦级)**：复杂舞弊排查（如存贷双高、大存大贷、体外资金循环），启动 MCTS 蒙特卡洛/ToT 假设树深度搜索。
2. **低开销甚至零开销机制**：
   - 在生产环境下，我们结合了**前置启发式规则引擎（正则+关键词特征向量，0 Token 开销）**与**受限语法解码（Constrained FSM / Pydantic JSON Schema）**。
   - 80% 的常见金融查询通过前置分流在 2ms 内完成判定；只有模糊意图才调用小参数量模型（如 GPT-4o-mini 或 Qwen-2.5-7B）做结构化分类，**整体节约了大模型 68% 的 API Token 成本，端到端延迟降低 4.2 倍**。

### Q4: MCTS（蒙特卡洛树搜索）在离散文本金融推理中到底如何落地？奖励函数（Reward）是如何设计的？

**【满分回答要点】**：
1. **状态与动作定义**：
   - **节点 State**：当前排查假设、已掌握的财报数据子表、已形成的线索链条；
   - **动作 Action**：四种离散排查动作（科目横向勾稽验算、深层附注穿透、贝尼斯 M-Score 操纵概率计算、跨期现金流调节）。
2. **确定性奖励函数 (Reward Formulation)**：
   - 与传统通过 LLM 拍脑袋打分不同，我们的 Simulation 阶段采用**客观金融指标作为硬奖励**：
     $$Reward = w_1 \cdot \mathbb{I}_{存贷双高} + w_2 \cdot (1 - \text{利息收益率}) + w_3 \cdot \text{Beneish\_M\_Score} + w_4 \cdot \text{未披露受限资金比率}$$
   - 例如：当货币资金占比超过 20%、带息负债占比超过 20%、且利息收益率低于 0.8% 时，直接触发重大舞弊高奖励（0.98），将风险值反向传播更新整条路径上的父节点 Q 值。
3. **Reflexion 反事实剪枝**：一旦模拟发现某条假设被真实勾稽关系证伪（例如高负债但利息收益率极其正常达 3.5%），立即标记为 Refuted 并削减访问概率，防止算法在死胡同里盲目发散。

### Q5: 评测大模型 Agent 时最容易踩“位置偏见（Position Bias）”和“自嗨评估”的坑，你们的“第四代双轨评测”是如何解决的？

**【满分回答要点】**：
1. **痛点剖析**：传统的 LLM-as-a-Judge 存在严重的位置偏见（模型倾向于选 Prompt 靠前或靠后的选项）、长度偏见（倾向于打分给废话长篇的回答）以及裁判自利偏见。
2. **轨 1：绝对容差代码直判**：
   - 完全摒弃 LLM 裁判，直接用沙箱计算的绝对误差判定：
     $$\text{Track 1 Error} = \frac{|y_{calc} - y_{ground\_truth}|}{y_{ground\_truth}} \le 0.1\%$$
   - 满足容差且舞弊判决与案卷真相吻合才算 Pass，标准比人类注册会计师更严苛。
3. **轨 2：协议双盲位置翻转去偏 (Swap Bias Test)**：
   - 在主观逻辑打分阶段，执行对称双盲调用：第一次评测 `(Report_A, Candidate_B)`，第二次将位置翻转为 `(Candidate_B, Report_A)`。
   - 只有当两次评测给出的判决完全一致（Consistency Check = True）时，该条评估才被采纳，有效剔除了 95% 以上的位置幻觉。

### Q6: 真实世界的上市公司年报通常长达 200~400 页，充斥着断表、跨页表格与畸形扫描件，你们在数据层是如何做鲁棒性防御的？

**【满分回答要点】**：
1. **跨页表头继承状态机**：普通解析器在跨页时常将第二页的第一行数据误判为表头。我们设计了全局表头记忆状态机，若当页表格无表头但列数与上一页对齐，自动继承上一页表头进行平滑拼接。
2. **DocumentChaosGuard（混乱度守卫）**：根据列对齐失真率、单元格空值率实时计算表格提取置信度评分（0.0 ~ 1.0）。
3. **多级平滑降级 (Graceful Degradation)**：
   - 级别一：文本直接规则提取；
   - 级别二：如果置信度低于 0.70 或扫描件扭曲，自动触发 OCR/视觉模型切片兜底；
   - 级别三：若表格仍然缺失，激活文本语义正则模式，从上下文段落中兜底捞取核心资产与负债科目挂载入沙箱。

### Q7: 为什么选择 DuckDB 而不是 SQLite 或传统 PostgreSQL？

**【满分回答要点】**：
1. **OLAP 列式引擎的天然契合性**：财报分析是典型的“高宽表、重聚合、跨列比率”分析。DuckDB 采用列式存储与向量化执行引擎，对百万行级财务数据的求和、方差、均值计算性能比按行存储的 SQLite 快 10~50 倍。
2. **零拷贝数据交换 (Zero-Copy)**：DuckDB 原生深度整合 Apache Arrow 和 Pandas，从 DataFrame 挂载到 SQL 查询，再从 SQL 查询导出为 DataFrame，几乎零序列化内存开销。
3. **轻量内嵌与极致并发**：它像 SQLite 一样作为进程内库运行，完全不需要维护独立的 DB 守护进程，沙箱执行完全在内存中完成，测试或并发执行完毕即销毁，天然避免考场数据交叉污染。

### Q8: 如果将该系统部署到大型商业银行或监管机构，并发量上升到 1000 QPS，架构瓶颈在哪里？如何横向扩容？

**【满分回答要点】**：
1. **瓶颈定位**：
   - 瓶颈不在于 FastAPI 或 DuckDB（单核 DuckDB 秒级能处理数万次轻量计算）；
   - 真正的瓶颈在于 **Tier 3 深度搜索中的外部大模型 API 调用配额 (RPM/TPM Rate Limits)** 与显存并发。
2. **扩容方案**：
   - **异步任务队列解耦**：将长时间的 MCTS 深度推演拆解为异步作业，采用 Celery + Redis / RabbitMQ 调度，客户端提交后通过 WebSocket 或轮询获取报告；
   - **沙箱无状态集群化**：DuckDB 全部使用 `:memory:` 临时实例，天然无状态，可通过 Kubernetes (K8s) 进行 Pod 的秒级 HPA 弹性横向伸缩；
   - **前缀缓存 (Prompt Prefix Caching) 优化**：将标准的中国企业会计准则 (CAS) 与通用财务科目 Prompt 进行静态前缀锁定，利用 vLLM 的 PagedAttention 机制复用 KV Cache，显存占用降低 60%，吞吐提升 3 倍。

### Q9: 你们导出的 Alpaca、ShareGPT、DPO 数据集，在模型微调（Post-Training）中到底有什么用？

**【满分回答要点】**：
1. **通用模型在金融垂直领域的致命缺陷**：通用底座（如 Qwen2.5、Llama3）喜欢“不懂装懂地心算”并生成通顺但错误的财务数值。
2. **SFT 阶段（行为塑形）**：通过 100 案卷的 Alpaca/ShareGPT 真实轨迹，强行给开源小模型注入“遇到复杂数字严禁心算，必须编写 Python/DuckDB 代码”的**行为模式 (Code-as-Action Bias)**。
3. **DPO 阶段（对齐偏好）**：
   - **Chosen（优选回答）**：严谨调用沙箱验算、多期背离交叉验证、给出明确证据链；
   - **Rejected（劣选回答）**：通顺的自然语言强行心算、模糊概括、无依据断言；
   - 通过 DPO 损失函数强化模型对“严谨金融刑侦证据链”的偏好权重，显著抑制商业落地中的幻觉。

### Q10: 整个项目中你个人觉得最有挑战的技术难点是什么？你是如何突破的？

**【建议回答结构（个人英雄时刻）】**：
- **难点**：在做 100 案金标准双轨评测时，如何确保裁判标准客观公正、杜绝假阳性（将正常波动误判为舞弊）和假阴性（漏报高隐蔽性造假）。
- **突破过程**：
  最初仅用通用 LLM 打分，发现模型对茅台等健康企业经常产生“莫须有”的质疑（因为负债不为0就过度敏感），导致准确率只有 78%。后来我做了两层手术：
  1. 引入“利息收益率背离度”与“受限资金未披露比率”作为硬质物理约束，只有当“存贷双高”且“利息收益率远低于市场利率（如 <0.8%）”时才定性为舞弊；
  2. 研发双盲翻转 Swap Bias Test 裁判协议，一旦模型因位置不同产生摇摆就启动三方裁决。
- **最终结果**：最终将 100 案的定性准确率从 78% 提升到了 **100.0%（TP=50, TN=50, 0误报0漏报）**，真正达到了可用于法庭质证与合规落地的工程水准。
